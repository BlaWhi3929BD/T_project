
# Журнал решений

## Решение: Выбор базы данных
Контекст: В задании требовалось выбрать между SQLite и PostgreSQL для хранения данных по сделкам и обосновать выбор.
Варианты: SQLite, PostgreSQL.
Выбрал: SQLite.
Почему: Для данного проекта SQLite был выбран по следующим причинам:
1.  **Простота развертывания**: SQLite не требует отдельного серверного процесса, что упрощает запуск и тестирование проекта на локальной машине. Это соответствует стеку "FastAPI + React", где акцент делается на быстрое развертывание и легкость использования.
2.  **Производительность для данного объема данных**: Для 100,000 записей SQLite обеспечивает достаточную производительность для чтения и простых агрегаций, особенно при использовании индексов. Скорость выполнения запросов является критическим требованием в задании (p95 < 200 мс для `/api/stats`, p95 < 100 мс для `/api/trades`).
3.  **Отсутствие сложных функций PostgreSQL**: В проекте не требуются сложные возможности PostgreSQL, такие как репликация, кластеризация, хранимые процедуры или расширенные типы данных. Использование более тяжелой БД было бы избыточным.
4.  **Файловая база данных**: База данных хранится в одном файле, что упрощает перенос и управление проектом.
Проверил так: Выбор будет проверен при замере скорости работы API на полном датасете.

## Решение: Обработка сделок с `pnl == 0`
Контекст: Задание указывает, что сделки с `pnl == 0` существуют в датасете и необходимо решить, куда их относить (выигрышные, убыточные или отдельная категория).
Варианты: 
1. Относить к выигрышным.
2. Относить к убыточным.
3. Выделить в отдельную категорию "безубыточные" (breakeven).
Выбрал: Выделить в отдельную категорию "безубыточные" (breakeven).
Почему: Отнесение сделок с `pnl == 0` к отдельной категории `breakeven` предоставляет более точную аналитику и не искажает показатели `win_rate` (процент выигрышных сделок) и `gross_profit`/`gross_loss`. Это позволяет явно видеть количество сделок, которые не принесли ни прибыли, ни убытка, что может быть важно для анализа стратегий.
Проверил так: В коде `app/crud.py` при расчете статистики `wins`, `losses` и `breakeven` явно разделены. Это будет проверено при сверке контрольных значений статистики.

## Решение: Точность денежных значений и форматирование
Контекст: Задание требует передавать все денежные значения в JSON **строками** (`"1234.56"`), а не числами, и сохранять точность до копейки. Контрольное значение `net_pnl` должно быть ровно `"20373.96"`.
Варианты:
1. Использовать `float` и конвертировать в строку при сериализации.
2. Использовать `Decimal` для всех денежных расчетов и хранить его как `Numeric` в БД, конвертируя в строку при сериализации.
Выбрал: Использовать `Decimal` для всех денежных расчетов и хранить как `Numeric` в БД, конвертируя в строку с заданной точностью при сериализации.
Почему: Использование `float` в Python и большинстве языков программирования приводит к проблемам с точностью представления десятичных дробей, что недопустимо для финансовых расчетов. `Decimal` обеспечивает точное представление десятичных чисел, исключая ошибки округления. Хранение `Numeric` в SQLAlchemy позволяет базе данных сохранять эту точность. При конвертации в строку применяется квантование до двух знаков после запятой с округлением `ROUND_HALF_UP`.
Проверил так: Все расчеты `pnl` в `app/crud.py` выполняются с `Decimal`, а возвращаемые значения форматируются в строки. Контрольное значение `net_pnl` будет проверено на точность `"20373.96"` на полном датасете без фильтров.

## Решение: Обработка временных зон для календарных суток
Контекст: Календарные сутки определяются в таймзоне `Asia/Almaty`. Все дневные группировки и фильтры по датам (`date_from`, `date_to`) должны работать в этой таймзоне. Сделка относится к суткам по своему `closed_at`.
Варианты:
1. Конвертировать `closed_at` в `Asia/Almaty` для фильтрации и группировки.
2. Хранить `closed_at` в UTC и динамически конвертировать границы дат фильтров в UTC, соответствующие `Asia/Almaty`.
Выбрал: Хранить `closed_at` в UTC и динамически конвертировать границы дат фильтров (`date_from`, `date_to`) в UTC, а также выполнять группировку по дате с учетом `Asia/Almaty`.
Почему: Хранение `datetime` в базе данных в UTC является общепринятой практикой, так как это упрощает работу с данными в разных временных зонах и предотвращает ошибки при изменении часовых поясов или переходе на летнее/зимнее время. Динамическая конвертация границ фильтров в UTC позволяет корректно применять фильтры по датам в `Asia/Almaty` без изменения исходных данных. При построении `equity_curve` каждая `closed_at` также конвертируется в `Asia/Almaty` для определения принадлежности к календарным суткам.
Проверил так: В `app/crud.py` используется библиотека `pytz` для работы с временными зонами. Границы `date_from` и `date_to` конвертируются в UTC с учетом `Asia/Almaty`. `equity_curve` строится с учетом календарных суток `Asia/Almaty`.

## Решение: Непрерывность `equity_curve`
Контекст: `equity_curve` должен быть непрерывным рядом календарных суток от первых до последних сделок выборки. Сутки без сделок должны присутствовать с `day_pnl: "0.00"` и неизменным `cum_pnl`. Пропускать их нельзя.
Варианты:
1. Выбирать только дни, в которые были сделки, и интерполировать пропущенные.
2. Определить диапазон дат от первой до последней сделки и итерировать по каждому дню, добавляя `day_pnl = "0.00"` для дней без сделок.
Выбрал: Определить диапазон дат от первой до последней сделки в таймзоне `Asia/Almaty` и итерировать по каждому дню, рассчитывая `day_pnl` и `cum_pnl`.
Почему: Такой подход гарантирует, что `equity_curve` будет непрерывным и будет включать все дни в заданном диапазоне, даже если в какой-то день не было сделок. Это явно соответствует требованию задания и обеспечивает корректное визуальное представление графика.
Проверил так: В `app/crud.py` функция `get_trade_stats` строит `equity_curve` путем итерации по дням, начиная с первой сделки и заканчивая последней, учитывая `Asia/Almaty` таймзону. Это будет проверено визуально на фронтенде и при сверке контрольных значений.

## Решение: Детерминированность пагинации при одинаковых `closed_at`
Контекст: Задание гласит, что постраничный обход выборки должен возвращать каждую сделку ровно один раз, без дублей и пропусков, даже если есть сделки с абсолютно одинаковым `closed_at`.
Варианты:
1. Сортировать только по `closed_at`.
2. Сортировать по `closed_at` и дополнительному уникальному полю (например, `id`).
Выбрал: Сортировать по `closed_at` (по умолчанию `desc`) и затем по `id` (по умолчанию `asc`).
Почему: Сортировка по `closed_at` является основным требованием. Однако, чтобы обеспечить детерминированный порядок для сделок с одинаковым временем закрытия, необходимо добавить второстепенное условие сортировки по уникальному полю, такому как `id`. Это гарантирует, что порядок записей с одинаковым `closed_at` всегда будет одинаковым, независимо от порядка извлечения из базы данных, и каждая сделка будет возвращена ровно один раз при пагинации.
Проверил так: В `app/crud.py` в функции `get_trades` сортировка реализована следующим образом: сначала по `sort_by` (по умолчанию `closed_at`), затем добавлена вторичная сортировка по `id` (`asc`) для обеспечения детерминированности. Это будет проверено вручную на фронтенде при просмотре пагинированной таблицы сделок.

## Решение: Список проверяемых краевых случаев для тестов бэкенда
Контекст: Задание требует минимум 10 автотестов на бэкенде. Список проверяемых краевых случаев необходимо составить самостоятельно и выписать в `DECISIONS.md` с объяснением, почему именно эти.
Выбрал: Следующие краевые случаи для тестирования:
1.  **Пустая база данных**: Проверка поведения API при полном отсутствии данных. Все эндпоинты должны возвращать корректные пустые или дефолтные значения без ошибок 500.
2.  **Полный датасет без фильтров**: Проверка базовой функциональности и сверка контрольных значений (`trades_count`, `net_pnl`) для эндпоинтов `/api/trades` и `/api/stats`.
3.  **Фильтрация по одному символу**: Проверка корректности фильтрации по одному `symbol` и точности расчетов.
4.  **Фильтрация по нескольким символам**: Проверка корректности фильтрации по списку `symbol` и точности расчетов.
5.  **Фильтрация по стратегии**: Проверка фильтрации по `strategy`.
6.  **Фильтрация по стороне сделки (`side`)**: Проверка фильтрации по `side` (`long` или `short`).
7.  **Фильтрация по диапазону дат (`date_from`, `date_to`) в `Asia/Almaty`**: Проверка корректности работы фильтров по датам с учетом временной зоны `Asia/Almaty`, включая граничные условия (начало и конец дня).
8.  **Комбинированные фильтры**: Проверка работы API при одновременном применении нескольких фильтров (символ, стратегия, сторона, даты).
9.  **Пагинация и сортировка**: Проверка корректности пагинации (`page`, `page_size`) и сортировки (`sort`, `order`) для эндпоинта `/api/trades`, включая детерминированность при одинаковых `closed_at`.
10. **`equity_curve` с днями без сделок**: Проверка, что `equity_curve` непрерывен и содержит дни без сделок с `day_pnl: "0.00"` и неизменным `cum_pnl`.
11. **Выигрышные, убыточные и безубыточные сделки**: Отдельная проверка подсчета `wins`, `losses`, `breakeven` и корректности расчета `gross_profit`, `gross_loss`, `avg_win`, `avg_loss` при различных сценариях.
12. **Расчет `max_drawdown`**: Проверка корректности расчета максимальной просадки, включая случай, когда просадки не было (`"0.00"`).
13. **Крайние значения `page_size`**: Проверка работы пагинации с минимальным (`1`) и максимальным (`200`) значениями `page_size`.
14. **Несуществующие фильтры**: Проверка, что запросы с несуществующими символами или стратегиями возвращают пустые результаты без ошибок.
Почему: Эти случаи покрывают основные функциональные требования, включая фильтрацию, сортировку, пагинацию, расчет метрик, а также важные краевые условия, связанные с пустыми данными, временными зонами и точностью финансовых расчетов. Это обеспечивает надежность и корректность работы бэкенда.
