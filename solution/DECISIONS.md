# Журнал решений

## Решение: Выбор базы данных

Контекст: Выбор между SQLite и PostgreSQL для хранения данных сделок.
Варианты: SQLite, PostgreSQL.
Выбрал: SQLite для локальной разработки.
Почему: Локальное хранение в одном файле упрощает запуск без Docker и PostgreSQL, а
для однопроцессного режима разработки обеспечивает необходимую скорость
выполнения запросов на 100 000 записей при использовании индексов.
Проверил так: Локальные API-тесты и нагрузочное тестирование при помощи `ab`
(Apache Benchmark) подтвердили корректность и приемлемую скорость.

## Решение: Место вычисления агрегатов
Контекст: Где считать статистику (бэкенд или фронтенд)?
Варианты: SQL-запросы на бэкенде, расчет на фронтенде после получения всех данных.
Выбрал: Бэкенд (SQL-агрегация и обработка результата в Python).
Почему: Расчет на фронтенде при 100к строк привел бы к фризам интерфейса.
Агрегация в SQL сокращает объём данных, передаваемых приложению, а Python
строит непрерывную equity curve.
Проверил так: Тесты API подтвердили время отклика < 200 мс на полном датасете.

## Решение: Определение выигрышной/убыточной сделки
Контекст: Как классифицировать сделки с PnL = 0?
Варианты: Прибавить к выигрышным, прибавить к убыточным, отдельная категория.
Выбрал: Отдельная категория `breakeven`.
Почему: Это обеспечивает максимальную точность метрик `win_rate` и `profit_factor`, исключая искажения, которые возникли бы при «принудительном» зачислении безубыточных сделок.
Проверил так: Тесты API подтвердили корректность раздельного подсчета `wins`, `losses` и `breakeven`.

## Решение: Детерминированность пагинации
Контекст: Как избежать дублей или пропусков при постраничном обходе данных с одинаковым `closed_at`?
Варианты: Сортировка только по `closed_at`, сортировка по `closed_at` + `id`.
Выбрал: Сортировка `closed_at` + `id`.
Почему: Добавление уникального `id` во второстепенный критерий сортировки делает порядок записей строго детерминированным, что гарантирует отсутствие дублей при смене страниц.
Проверил так: Тестовый скрипт прошел полный обход датасета без обнаружения дубликатов.

## Решение: Хранение состояния дашборда
Контекст: Как обеспечить передачу состояния фильтров через ссылку?
Варианты: LocalStorage, URL-параметры.
Выбрал: URL-параметры.
Почему: Использование URL позволяет пользователю копировать ссылку, пересылать её коллегам, а также использовать кнопки «Назад»/«Вперед» в браузере.
Проверил так: Ручная проверка пересылки ссылки с активными фильтрами; состояние корректно восстанавливается.

## Решение: Точность финансовых вычислений
Контекст: Обеспечение точности до копейки (контрольное значение `net_pnl` = "20373.96").
Варианты: Использование `float`, использование `Decimal`.
Выбрал: `Decimal` (Python) + `Numeric` (SQLAlchemy).
Почему: `float` не гарантирует точность десятичных дробей. `Decimal` исключает ошибки округления. При передаче в JSON значения конвертируются в `str`, сохраняя точность.
Проверил так: Сверка контрольного значения `net_pnl` ("20373.96") приемочным скриптом.

## Решение: Переход на PostgreSQL для развёртывания

Контекст: Переход от локального SQLite к клиент-серверной СУБД в контейнеризованном окружении (Docker Compose и Kubernetes).
Варианты: Сохранение SQLite, переход на PostgreSQL.
Выбрал: PostgreSQL.
Почему: SQLite в контейнерах имеет ограничения при параллельной записи (lock файла базы) и масштабировании бэкенда на несколько реплик (`replicas > 1`). PostgreSQL обеспечивает полноценный многопользовательский доступ, горизонтальное масштабирование реплик API и корректную работу со сетевыми томами (StatefulSet / Persistent Volume) в Kubernetes.
Проверил так: Выполнены интеграционные тесты API с подключением к PostgreSQL; результаты расчётов статистики (`net_pnl`, `max_drawdown` и др.) идентичны SQLite до копейки.

## Решение: Выбор Kubernetes платформы для разработки

Контекст: Выбор локального Kubernetes кластера для разработки и тестирования.
Варианты: `kind`, `minikube`.
Выбрал: `minikube`.
Почему: `minikube` является проверенным стандартом индустрии для локального воспроизведения продакшн-окружения на любых ОС, включает богатый набор встроенных дополнений (`addons`, например, `ingress`) из коробки и более привычен для тестирования взаимодействия с Ingress-контроллером без необходимости ручного конфигурирования NodePort на хосте.
Проверил так: Интеграция Ingress-контроллера через `minikube addons enable ingress` и проброс через туннель отработали без сбоев.

## Решение: Инструмент шаблонизации манифестов Kubernetes

Контекст: Выбор средства оркестрации и упаковки манифестов приложения.
Варианты: `Helm`, `kustomize`.
Выбрал: `kustomize`.
Почему: Наше приложение имеет фиксированную архитектуру без необходимости сложной логики шаблонизации. `kustomize` встроен в `kubectl` (`kubectl apply -k`), не требует отдельного Helm-клиента и файлов `values.yaml`, а также позволяет декларативно переопределять неймспейс и общие метки.
Проверил так: Развертывание всего стека ресурсов выполняется одной командой `kubectl apply -k k8s/` без ошибок.

## Решение: Жизненный цикл загрузки данных

Контекст: Где и когда генерировать CSV и загружать его в PostgreSQL при запуске контейнеров.
Варианты: Отдельный Compose-сервис или Kubernetes Job, загрузка в entrypoint backend.
Выбрал: Идемпотентный seed в entrypoint backend до запуска Uvicorn.
Почему: Один жизненный цикл одинаково работает в Docker Compose и Kubernetes, не требует
координации отдельного сервиса или неизменяемого Job и не позволяет backend стать
готовым до завершения первичной загрузки. Загрузка выполняется в одной транзакции:
прерванная операция откатывается, а следующий запуск повторяет её.
Проверил так: Повторный запуск сообщает о пропуске полного датасета, а backend-тесты и
Compose smoke-тест подтверждают контрольные значения статистики.

## Решение: Передача секретов Kubernetes

Контекст: Как передавать пароль PostgreSQL и `DATABASE_URL` при развёртывании.
Варианты: Secret в Git, Kustomize `secretGenerator` из файла в Git, создание Secret
командой перед `kubectl apply`.
Выбрал: Создание Secret вне репозитория через `kubectl create secret`.
Почему: Реальные credentials не попадают в Git, Docker history или Kustomize output.
Манифесты используют `secretKeyRef`, а оператор передаёт значения непосредственно
кластеру перед установкой.
Проверил так: `git grep` не содержит рабочего пароля, а `kubectl apply -k k8s/`
использует заранее созданный Secret.

## Решение: Startup probe для backend

Контекст: Первый запуск backend выполняет генерацию CSV и полный seed до старта
Uvicorn, поэтому контейнер может долго не отвечать на HTTP-пробы.
Варианты: Увеличить только `initialDelaySeconds`, добавить `startupProbe`,
вынести seed в отдельный Kubernetes Job.
Выбрал: `startupProbe` на `/health` с окном ожидания до 10 минут.
Почему: Kubernetes не запускает liveness- и readiness-проверки до успешного
startup probe. Это предотвращает преждевременный перезапуск pod во время
первичной загрузки и сохраняет единый lifecycle seed в entrypoint backend.
После успешного старта liveness проверяет живой процесс, а readiness проверяет
доступность PostgreSQL через `/ready`.
Проверил так: Kustomize-рендеринг содержит startup probe с 60 попытками по 10
секунд; backend и Compose lifecycle-тесты сохраняют контрольные значения после
первого и повторного запуска.

## Решение: Обновление тегов образов Kustomize

Контекст: Локальные Kubernetes-образы собираются с коротким SHA коммита, а
Deployment использует `IfNotPresent`. Нужно гарантировать, что новый образ
действительно попадёт в Pod после повторного обновления.
Варианты: Ручная замена `latest` через `sed`, редактирование YAML вручную,
`kustomize edit set image`.
Выбрал: Идемпотентная замена `newTag` через `sed` или PowerShell regex.
Почему: Команда заменяет любое текущее значение `newTag`, поэтому остаётся
идемпотентной при последовательных обновлениях с разными SHA. Новый tag
изменяет Pod template, а отказ от `latest` исключает использование старого
локального образа при `imagePullPolicy: IfNotPresent`.
Проверил так: README содержит повторяемую Bash/fish и PowerShell команды, а CI
отвергает отрендерированные манифесты с тегом `latest`.

## Решение: Kustomize overlays для окружений

Контекст: Локальный minikube и production требуют разных масштабов backend, но
должны использовать один набор базовых ресурсов.
Варианты: Дублировать манифесты, Helm values, Kustomize base с overlays.
Выбрал: Kustomize base с `local` и `production` overlays.
Почему: Общая конфигурация ресурсов хранится в одном месте, а окружения
переопределяют только image tags и параметры deployment. Local overlay
сохраняет одну реплику для minikube, production использует две реплики
backend и `PodDisruptionBudget` с `maxUnavailable: 0`.
Проверил так: `kubectl kustomize k8s/` и
`kubectl kustomize k8s/overlays/production/` успешно рендерят ресурсы;
production-вывод содержит две реплики и PDB, а root-путь сохраняет
совместимую команду `kubectl apply -k k8s/`.

## Решение: Оптимизация статистики и конкурентных запросов

Контекст: `/api/stats` строит непрерывную equity curve по 100 000 сделок, а
обработчики используют синхронный SQLAlchemy. Двойной полный проход по таблице
и один Uvicorn worker ухудшали p95 при пяти параллельных запросах.
Варианты: Добавить внешний кэш, загружать все сделки в pandas, объединить
дневные и глобальные агрегаты, увеличить число Uvicorn workers.
Выбрал: Один SQL `GROUP BY` по календарному дню с последующим объединением
агрегатов из дневных строк и два Uvicorn workers.
Почему: База выполняет один проход и возвращает только дневные строки, а
Python сохраняет Decimal-округление и строит пропущенные дни. Два worker-процесса
позволяют конкурентным sync-запросам выполняться независимо. Внешний кэш не
нужен и не добавляет отдельное состояние.
Проверил так: контрольные значения `trades_count=100000` и
`net_pnl="20373.96"` сохранены, SQLite/PostgreSQL parity-тесты проходят, а
`EXPLAIN ANALYZE` показывает hash aggregation без сортировки 100 000 строк.
